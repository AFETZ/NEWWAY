# 2 Разработка инструментальной среды совместного имитационного моделирования влияния V2X-коммуникаций на поведение транспортных средств

## 2.1 Требования к инструментальной среде

На основании теоретического обзора, представленного в главе 1, были сформулированы требования к инструментальной среде, необходимой для исследования влияния деградации V2X-обмена на поведение подключенных транспортных средств. Требования сгруппированы по четырем категориям: архитектурные, функциональные, доказательные и воспроизводимостные.

### 2.1.1 Архитектурные требования

1. **Двунаправленное сопряжение транспортного и сетевого симуляторов.** Среда должна обеспечивать не одностороннюю передачу информации от транспортной модели к сетевой, а замкнутый контур: сетевые события (потери, задержки) должны влиять на решения транспортных агентов, а изменение траекторий — на условия радиораспространения.

2. **Поддержка множественных радиотехнологий V2X.** Для сравнительного анализа необходима поддержка IEEE 802.11p, LTE-V2X (Mode 4) и NR-V2X (Mode 2) в рамках единого эксперимента без смены инструментальной платформы.

3. **Интеграция геометрически чувствительной модели канала.** Для задач, где результат зависит от пространственной конфигурации сцены, среда должна поддерживать подключение ray-tracing модуля (Sionna RT) в реальном времени моделирования.

4. **Модульность прикладного уровня.** Алгоритмы реакции транспортного агента на V2X-сообщения должны быть параметризуемы и изменяемы без модификации нижележащих сетевых и транспортных уровней.

### 2.1.2 Функциональные требования

1. **Управляемое инжектирование деградации связи** на нескольких уровнях: на уровне приложения (rx-drop-prob-cam), на уровне физического уровня (rx-drop-prob-phy-cam) и через профили мощности передатчика (per-vehicle-prr-profile).

2. **Индивидуальные профили связи для каждого транспортного средства** — возможность задать для каждого участника собственную эквивалентную мощность передатчика, целевой PRR и вероятность потери на физическом уровне.

3. **Инцидентный режим** — управляемая генерация транспортных событий (остановка на полосе, создание препятствия) в заданный момент времени.

4. **Поддержка ETSI-сервисов** — CAM, DENM, CPM — с корректной генерацией, диссеминацией и приемом согласно спецификациям ETSI.

### 2.1.3 Доказательные требования

1. **Идентификационно-связанная трассировка пакетов** (ID-aware packet tracing) — каждый передаваемый пакет должен иметь уникальный идентификатор (`pkt_uid`), сохраняемый на всех этапах: передача, прием, потеря на физическом уровне, реакция прикладного уровня.

2. **Многоуровневое логирование** — раздельные потоки данных для сообщений (MSG.csv), управляющих действий (CTRL.csv), профилей (PROFILE.csv) и транспортных состояний (netstate.xml, collision.xml).

3. **Автоматизированный causal-аудит** — возможность программной реконструкции причинно-следственной цепочки «потеря пакета → отсутствие маневра → столкновение» без ручного анализа логов.

### 2.1.4 Требования воспроизводимости

1. **Детерминированность при фиксированных параметрах** — при одинаковых seed, конфигурациях и версиях ПО результаты должны быть идентичны.

2. **Автоматизированный запуск** — весь эксперимент (сборка, конфигурирование, запуск, постобработка) выполняется одной командой.

3. **Структурированный формат выходных артефактов** — CSV, XML и PNG с единой системой именования для автоматической обработки.

## 2.2 Выбор базовой платформы и обоснование архитектурных решений

### 2.2.1 Обоснование выбора ms-van3t как базового фреймворка

В качестве базовой платформы для разработки был выбран фреймворк ms-van3t [31], представляющий собой интегрированную многостековую среду виртуальной валидации V2X-коммуникаций и сервисов на основе ns-3. Выбор обусловлен следующими факторами:

1. **Многотехнологическая поддержка.** ms-van3t включает реализации IEEE 802.11p, LTE-V2X (Mode 4) и NR-V2X (Mode 2), что позволяет проводить сравнительные эксперименты без смены платформы.

2. **Наличие ETSI Facilities Layer.** Фреймворк реализует сервисы CA Basic Service (CAM), DEN Basic Service (DENM) и CP Basic Service (CPM), включая ASN.1-кодирование/декодирование, что обеспечивает корректную генерацию и обработку стандартизованных V2X-сообщений.

3. **Двунаправленная интеграция с SUMO.** Через интерфейс TraCI обеспечивается синхронная работа ns-3 и SUMO с пошаговым обменом данными: ns-3 получает координаты и скорости от SUMO, а при необходимости может изменять скорость и полосу движения через команды TraCI.

4. **Расширяемость прикладного уровня.** Архитектура ms-van3t предусматривает возможность создания пользовательских приложений (ns-3 Application), наследующих от базового класса и получающих обратные вызовы при приеме CAM, DENM и CPM.

### 2.2.2 Интеграция с Sionna RT

Для реализации геометрически чувствительного моделирования канала в состав инструментальной среды был интегрирован модуль NVIDIA Sionna RT [32]. Интеграция реализована по следующей схеме:

- Модуль Sionna запускается как внешний GPU-сервер, принимающий по UDP запросы на расчет параметров канала для заданных позиций передатчика и приемника.
- На стороне ns-3 при каждом шаге моделирования формируется запрос, содержащий трехмерные координаты транспортных средств, полученные от SUMO через TraCI.
- Sionna выполняет лучевую трассировку с учетом геометрии сцены (здания, рельеф) и возвращает параметры канала (затухание, доплеровский сдвиг).
- Полученные параметры используются для определения факта успешного приема каждого пакета.

Такая архитектура позволяет при необходимости заменить Sionna RT на другую модель канала без модификации прикладного и транспортного уровней.

### 2.2.3 Общая архитектура инструментальной среды

Итоговая архитектура инструментальной среды представлена на рисунке 2.1 и включает четыре основных компонента:

**Рисунок 2.1 — Архитектура инструментальной среды совместного моделирования**

```
┌─────────────────────────────────────────────────────────────────┐
│                     Прикладной уровень                         │
│   emergencyVehicleAlert (CAM/DENM/CPM → решение → маневр)     │
│   ┌─────────┐ ┌──────────┐ ┌──────────┐ ┌──────────────────┐  │
│   │ MSG.csv │ │ CTRL.csv │ │PROFILE.csv│ │ collision.xml    │  │
│   └─────────┘ └──────────┘ └──────────┘ └──────────────────┘  │
├─────────────────────────────────────────────────────────────────┤
│                   ETSI Facilities Layer                         │
│   CA Basic Service │ DEN Basic Service │ CP Basic Service      │
│   Local Dynamic Map (LDM) │ Vehicle Data Provider (VDP)        │
├─────────────────────────────────────────────────────────────────┤
│                 Сетевой и транспортный уровни                  │
│   BTP │ GeoNetworking │ DCC (адаптивный/реактивный)           │
├─────────────────────────────────────────────────────────────────┤
│              Канальный и физический уровни                      │
│   IEEE 802.11p │ LTE-V2X Mode 4 │ NR-V2X Mode 2              │
│   ┌──────────────────────────────────────────┐                 │
│   │ Sionna RT (GPU ray-tracing) / GEMV2      │                 │
│   └──────────────────────────────────────────┘                 │
├─────────────────────────────────────────────────────────────────┤
│               Транспортный симулятор (SUMO)                     │
│   TraCI ←→ ns-3: координаты, скорости, полосы, инцидент       │
│   netstate.xml │ collision.xml                                  │
└─────────────────────────────────────────────────────────────────┘
```

Взаимодействие компонентов организовано следующим образом:

1. **SUMO → ns-3:** на каждом шаге моделирования SUMO через TraCI передает в ns-3 текущие координаты, скорости и полосы движения всех транспортных средств. Эти данные используются для расчета расстояний между транспортными средствами и условий радиораспространения.

2. **ns-3 → SUMO:** при срабатывании прикладной логики реакции (приём CAM с предупреждением, обнаружение опасности) ns-3 отправляет через TraCI команды изменения скорости (`slowDown`) и/или принудительной смены полосы (`changeLane`) для соответствующего транспортного средства.

3. **ns-3 ↔ Sionna RT:** координаты транспортных средств передаются в Sionna для расчета параметров канала; результаты возвращаются для определения условий приема пакетов.

## 2.3 Разработка приложения emergencyVehicleAlert

### 2.3.1 Назначение и функциональная роль

Центральным элементом прикладного уровня инструментальной среды является приложение `emergencyVehicleAlert`, реализованное как класс C++, наследующий от `ns3::Application`. Приложение устанавливается на каждый узел ns-3, соответствующий транспортному средству в SUMO, и выполняет следующие функции:

- приём и обработку CAM, DENM и CPM от соседних транспортных средств;
- оценку опасности на основе расстояния, направления движения и разницы курсов;
- формирование управляющего решения (перестроение, снижение скорости, отсутствие действия);
- логирование всех событий приема, потери и реакции с привязкой к `pkt_uid`.

### 2.3.2 Алгоритм обработки CAM-сообщений

При получении CAM-сообщения приложение выполняет следующую последовательность действий:

1. **Извлечение кинематических данных** — из ASN.1-структуры CAM извлекаются координаты, скорость и направление движения отправителя.

2. **Вычисление расстояния** — рассчитывается расстояние от приемника до отправителя с использованием формулы гаверсинуса по географическим координатам.

3. **Вычисление разницы курсов** — определяется абсолютная разница между направлениями движения приемника и отправителя.

4. **Проверка пороговых условий** — если расстояние меньше порога `cam-reaction-distance-m` и разница курсов попадает в допустимый диапазон, генерируется событие реакции.

5. **Формирование управляющего действия** — при срабатывании условий через TraCI отправляются команды:
   - `changeLane(target_lane)` — принудительная смена полосы на целевую;
   - `slowDown(target_speed)` — снижение скорости до заданного значения.

6. **Логирование** — событие записывается в CTRL.csv с указанием типа (`cam_reaction`), идентификатора отправителя (`tx_id`), идентификатора пакета (`pkt_uid`), расстояния, разницы курсов, полос до и после маневра.

### 2.3.3 Механизм индивидуальных профилей связи (per-vehicle-prr-profile)

Ключевым нововведением является механизм индивидуальных профилей связи, позволяющий задать для каждого транспортного средства собственные параметры радиолинии. Профиль задается через параметр командной строки в формате:

```
--per-vehicle-prr-profile=vehId:rxDropPhyCam[:equiv_dBm[:targetPRR[:rxDropPhyCpm]]]
```

Например:
```
veh3:0.05:23:0.95,veh4:0.923:-20:0.077,veh5:0.307:0:0.693
```

При инициализации приложения строка профиля разбирается, и для каждого транспортного средства формируется структура `PerVehiclePrrProfile`:

```cpp
struct PerVehiclePrrProfile {
    double rx_drop_prob_phy_cam;     // вероятность потери CAM на PHY-уровне
    double rx_drop_prob_phy_cpm;     // вероятность потери CPM на PHY-уровне
    double equiv_tx_power_dbm;       // эквивалентная мощность передатчика (dBm)
    double target_prr;               // целевой PRR
};
```

При приеме каждого пакета генерируется случайное число от 0 до 1 с помощью равномерного генератора `m_drop_rv`. Если сгенерированное значение меньше `rx_drop_prob_phy_cam`, пакет отбрасывается на физическом уровне и регистрируется как `CAM_DROP_PHY`. Метаданные профиля (`equiv_tx_power_dbm`, `target_prr`) записываются в PROFILE.csv для последующей верификации.

Данный механизм позволяет в рамках одного прогона моделировать ситуацию, когда одни транспортные средства имеют качественную связь (высокий PRR), а другие — деградированную, что является необходимым условием для демонстрации дифференцированного влияния связи на поведение.

### 2.3.4 Механизм инжектирования инцидента

Для создания управляемой опасной ситуации реализован механизм инцидента. При активации параметров `--incident-enable=1`, `--incident-vehicle-id=vehX`, `--incident-time-s=T` в заданный момент времени `T` для указанного транспортного средства через TraCI выполняется остановка на текущей полосе. Инцидент фиксируется в логе как:

```
INCIDENT-APPLIED,id=vehX,time_s=T,...
```

Параметры `collision.action=warn` и `collision.stoptime=1000` в конфигурации SUMO обеспечивают, что столкнувшиеся транспортные средства остаются на дороге, формируя устойчивое место ДТП. Факт столкновения регистрируется в `collision.xml` с указанием времени, участников, полосы и позиции.

### 2.3.5 Система crash-mode для принудительного столкновения

Для сценариев, в которых требуется гарантированная демонстрация столкновения при высоких потерях, реализован механизм crash-mode. Он активируется при выполнении условия: транспортное средство (задаваемое через `--crash-mode-vehicle-id`) накопило серию из `N` последовательных решений `drop_decision_no_action` без единого компенсирующего маневра (параметр `--crash-mode-no-action-threshold`).

При срабатывании crash-mode транспортному средству через TraCI задается форсированная скорость (`--crash-mode-force-speed-mps`), направленная к препятствию, на заданную длительность (`--crash-mode-duration-s`). Данный механизм можно отключить (`--crash-mode-enable=0`), что используется в контрольных экспериментах для подтверждения того, что результат не является следствием искусственного механизма.

## 2.4 Система идентификационно-связанной трассировки пакетов

### 2.4.1 Архитектура pkt_uid-трассировки

Одним из ключевых элементов разработанной инструментальной среды является сквозная идентификационная трассировка пакетов, обеспечивающая однозначное сопоставление событий на разных уровнях системы. Каждому передаваемому CAM-сообщению присваивается уникальный идентификатор `pkt_uid`, который сохраняется на всех этапах жизненного цикла пакета:

1. **Передача (TX):** при генерации CAM записывается `{tx_t_s, tx_id, msg_seq, pkt_uid}` в MSG.csv отправителя.

2. **Успешный прием (RX):** при доставке CAM на прикладной уровень приемника записывается `{rx_t_s, tx_id, msg_seq, pkt_uid, msg_type=CAM}` в MSG.csv приемника.

3. **Потеря на физическом уровне (DROP_PHY):** при отбрасывании пакета на физическом уровне записывается `{rx_t_s, tx_id, msg_seq, pkt_uid, msg_type=CAM_DROP_PHY}` в MSG.csv приемника с вызовом `LogPhyDropEvent`.

4. **Решение прикладного уровня (CTRL):** реакция или отсутствие реакции записывается в CTRL.csv с указанием `{time_s, event_type, tx_id, msg_seq, pkt_uid, distance_m, heading_diff_deg, lane_before, lane_after, speed_target}`.

### 2.4.2 Типы управляющих событий

В системе определены следующие типы управляющих событий, регистрируемых в CTRL.csv:

**Таблица 2.1 — Типы управляющих событий в CTRL.csv**

| Тип события | Описание | Условие возникновения |
|---|---|---|
| `cam_reaction` | Реакция на принятый CAM | Расстояние < порога, курс совпадает, условия выполнены |
| `cpm_reaction` | Реакция на принятый CPM | TTC < порога, расстояние < порога |
| `sensor_reaction` | Реакция на данные локального сенсора | Обнаружение объекта в зоне действия сенсора |
| `drop_decision_no_action` | Зафиксирована потеря, но действие не предпринято | Пакет отброшен на PHY, прикладная реакция отсутствует |
| `crash_mode_forced_speed` | Форсированная скорость crash-mode | Порог no_action-серии превышен |
| `cam_reaction_no_maneuver` | CAM принят, но маневр не требуется | Расстояние или курс вне диапазона реакции |

### 2.4.3 Механизм корреляции DROP → DECISION

Для автоматизированного связывания потерь пакетов с решениями прикладного уровня разработан скрипт `build_drop_decision_timeline.py`. Алгоритм работает следующим образом:

1. Из MSG.csv извлекаются все события типа `CAM_DROP_PHY` с их `pkt_uid`.
2. Из CTRL.csv извлекаются все события с тем же `pkt_uid`.
3. Формируется `event_timeline.csv`, содержащий пары `{DROP_PHY, time_drop} → {DECISION, time_decision, decision_type}`.
4. Вычисляются агрегированные статистики: доля match-ов, медианная задержка, распределение типов решений.

Результат записывается в `summary.csv`:

```csv
metric,value
vehicles_scanned,3
total_drop_events,787
matched_decision_events,787
strict_match_ratio,1.0
reaction_events,0
no_action_events,787
lane_change_events,0
median_decision_delay_s,0.0
p95_decision_delay_s,0.0
```

Strict match ratio = 1.0 подтверждает, что каждая потеря пакета имеет соответствующее решение прикладного уровня.

## 2.5 Система автоматизированного causal-аудита столкновений

### 2.5.1 Назначение

Автоматизированный causal-аудит предназначен для формальной реконструкции причинно-следственной связи между сетевыми потерями и транспортным столкновением. Аудит выполняется скриптом `build_collision_causality_report.py` и формирует структурированный отчет, включающий:

- идентификацию участников столкновения из `collision.xml`;
- анализ окна событий перед моментом столкновения;
- подсчет drop-событий и no_action-решений в этом окне;
- классификацию силы причинной связи.

### 2.5.2 Формат выходных данных

Результат causal-аудита записывается в `collision_causality.csv`:

```csv
collision_time_s,collider,victim,drop_events_window,no_action_events_window,
last_drop_time_s,last_decision_event_type,causal_evidence
7.95,veh4,veh2,179,179,7.94933,drop_decision_no_action,strong_no_action_only
```

Поле `causal_evidence` принимает значения:
- `strong_no_action_only` — в окне перед столкновением отсутствовали компенсирующие реакции, преобладали no_action;
- `mixed` — присутствовали как потери, так и реакции;
- `weak` — недостаточно данных для уверенной атрибуции.

### 2.5.3 Интерпретация для доказательной базы

Значение `strong_no_action_only` означает, что в окне перед столкновением для указанного транспортного средства не наблюдалось компенсирующей реакции, а доминирующим паттерном оставались потери и решения типа `drop_decision_no_action`. Это позволяет утверждать, что столкновение имеет не только визуальное, но и логически реконструируемое объяснение через цепочку сетевых событий.

### 2.7.2 Генерация цепочки «dBm → PRR → маневр → исход»

Скрипт `build_valid_scenario_intuitive_plots.py` реализует сквозную аналитическую цепочку, связывающую параметры радиолинии с транспортным исходом. Для каждого транспортного средства формируется запись:

```csv
vehicle,equiv_tx_power_dbm,target_prr,observed_prr,prr_error,
first_decision_event,first_decision_time_s,first_lane_change_time_s,
collision,decision_outcome
```

Поле `decision_outcome` принимает одно из значений:
- `maneuver_before_collision` — маневр выполнен до момента столкновения (безопасный исход);
- `no_maneuver_before_collision` — маневр не выполнен до столкновения (аварийный исход);
- `late_maneuver_after_collision` — маневр выполнен после столкновения (формально поздняя реакция);
- `no_collision_safe` — столкновения не произошло.

Данный формат позволяет в одной таблице увидеть полную причинную цепочку для каждого участника эксперимента.

### 2.7.3 Расчет метрик безопасности из транспортных данных

Скрипт `analyze_netstate_collision_risk.py` выполняет парсинг XML-файла SUMO netstate и вычисляет:

- **Minimum gap** — минимальное расстояние между последовательными транспортными средствами на полосе;
- **Minimum TTC** — минимальное значение Time-to-Collision, рассчитанное как $TTC = gap / \Delta v$ при $\Delta v > 0$;
- **Risky TTC events** — количество моментов, когда TTC опускается ниже заданного порога (по умолчанию 3.0 с);
- **Risky gap events** — количество моментов, когда gap опускается ниже заданного порога (по умолчанию 5.0 м).

Результаты записываются в `collision_risk_summary.csv` и визуализируются в `collision_risk_timeseries.png`.

## 2.8 Конфигурация транспортных сценариев в SUMO

### 2.8.1 Дорожная сеть и маршруты

Для экспериментальных сценариев используется дорожная сеть `map.net.xml`, представляющая замкнутую четырехполосную дорогу. Маршруты транспортных средств определяются в файлах `.rou.xml`:

- `cars_incident_threeflow.rou.xml` — основной сценарий с тремя следующими транспортными средствами в одной полосе за инцидентным;
- `intersection.rou.xml` — сценарий перекрестка с пересекающимися маршрутами.

Конфигурация SUMO фиксирует шаг моделирования 0.1 с, длительность симуляции и параметры обработки столкновений:

```xml
<configuration>
    <input>
        <net-file value="map.net.xml"/>
        <route-files value="cars_incident_threeflow.rou.xml"/>
    </input>
    <time>
        <begin value="0"/>
        <end value="300"/>
        <step-length value="0.1"/>
    </time>
    <processing>
        <collision.action value="warn"/>
        <collision.stoptime value="1000"/>
    </processing>
</configuration>
```

### 2.8.2 Параметры транспортных средств

Для основного сценария используются следующие параметры:
- максимальная скорость: 50 км/ч (13.89 м/с);
- модель следования: Krauss (по умолчанию в SUMO);
- время реакции: 1.0 с;
- минимальный зазор: 2.5 м.

## 2.9 Поддержка множественных радиотехнологий

### 2.9.1 Конфигурация стеков V2X

Инструментальная среда поддерживает три радиотехнологии, переключаемые через выбор соответствующего бинарного файла симуляции:

**Таблица 2.4 — Поддерживаемые радиотехнологии V2X**

| Технология | Бинарный файл | Частота | Полоса | Особенности |
|---|---|---|---|---|
| IEEE 802.11p | `v2v-emergencyVehicleAlert-80211p` | 5.9 GHz | 10 MHz | DCC, CSMA/CA, низкая задержка (~0.5 мс) |
| LTE-V2X Mode 4 | `v2v-emergencyVehicleAlert-ltev2x` | Band 47 | 10 MHz | SPS, полу-статическое распределение ресурсов |
| NR-V2X Mode 2 | `v2v-emergencyVehicleAlert-nrv2x` | Band n47 | 10 MHz | Sensing + SCI, автономное распределение ресурсов |

Все три варианта используют одинаковый прикладной уровень (`emergencyVehicleAlert`) и одинаковые параметры реакции, что обеспечивает корректность сравнения.

### 2.9.2 Данные кросс-технологического сравнения

В результате проведенных экспериментов получены следующие характеристики для co-existence сценария (10 узлов, стандартные условия):

**Таблица 2.5 — Сравнительные характеристики радиотехнологий V2X**

| Метрика | IEEE 802.11p | NR-V2X Mode 2 |
|---|---|---|
| Средний PRR | 0.920 | 0.962 |
| Диапазон PRR | 0.789 – 1.000 | 0.826 – 1.000 |
| Средняя задержка | 0.49 мс | 12.3 мс |
| Диапазон задержки | 0.44 – 0.64 мс | 7.7 – 16.8 мс |
| Узлы с PRR = 1.0 | 5 из 10 | 2 из 10 |

Полученные данные показывают характерный компромисс: IEEE 802.11p обеспечивает меньшую задержку при сопоставимом PRR, тогда как NR-V2X демонстрирует более высокий средний PRR при существенно большей задержке. Для задач, чувствительных к временному бюджету доставки сообщения, данное различие может быть определяющим.

## 2.10 Интеграция с Sionna RT: архитектура и верификация

### 2.10.1 Протокол взаимодействия

Sionna RT запускается как Python-скрипт на GPU-сервере и принимает UDP-дейтаграммы, содержащие:
- координаты и высоту передатчика;
- координаты и высоту приемника;
- частоту несущей;
- полосу пропускания.

В ответ возвращаются:
- коэффициент затухания на пути (path loss, dB);
- доплеровский сдвиг (Hz);
- импульсный отклик канала (CIR).

На стороне ns-3 полученный path loss используется для определения SNR и сравнения с порогом чувствительности приемника.

### 2.10.2 Верификация подключения Sionna

Для подтверждения реального использования ray-tracing в эксперименте в логе фиксируется маркер:
```
SUCCESS! ns-3 is now locally connected to Sionna
```

Дополнительно в PRR-данных для Sionna-прогонов наблюдается характерная зависимость PRR от расстояния:
- ближние узлы (до 100 м): PRR 0.62–0.84;
- средние узлы (100–200 м): PRR 0.95–1.0;
- дальние узлы (>200 м): PRR ~1.0.

Такая зависимость отражает влияние геометрии сцены на канал (NLOS, отражения от зданий), что подтверждает корректность работы модуля ray-tracing.

## 2.11 Выводы по главе разработки

В данной главе описана разработка инструментальной среды совместного имитационного моделирования, предназначенной для исследования влияния V2X-коммуникаций на поведение подключенных транспортных средств. Получены следующие результаты.

1. **Реализована двунаправленная интеграция** транспортного симулятора SUMO, сетевого симулятора ns-3 и модуля лучевой трассировки Sionna RT. Двунаправленность подтверждается тем, что сетевые потери приводят к транспортным исходам (столкновение), а изменение траекторий влияет на условия радиораспространения.

2. **Разработано приложение `emergencyVehicleAlert`** с поддержкой CAM, DENM и CPM, индивидуальными профилями связи для каждого транспортного средства и параметризуемой логикой реакции на основе расстояния, курса и TTC.

3. **Реализована система идентификационно-связанной трассировки пакетов** (`pkt_uid`), обеспечивающая однозначное сопоставление событий физического уровня (потери) с решениями прикладного уровня (маневр / отказ) и транспортными исходами (столкновение / безопасный объезд).

4. **Разработана система автоматизированного causal-аудита**, формализующая причинно-следственную связь «потеря → отсутствие маневра → столкновение» в машиночитаемом формате с классификацией силы доказательства.

5. **Создана система автоматизированного запуска и постобработки**, позволяющая воспроизвести полный цикл эксперимента одной командой с формированием структурированных артефактов (CSV, XML, PNG).

6. **Обеспечена поддержка трех радиотехнологий V2X** (IEEE 802.11p, LTE-V2X, NR-V2X) в рамках единого прикладного уровня, что позволяет проводить кросс-технологические сравнения при прочих равных условиях.

Разработанная инструментальная среда удовлетворяет всем сформулированным требованиям и создает необходимую основу для проведения экспериментальной апробации, описанной в главе 3.
