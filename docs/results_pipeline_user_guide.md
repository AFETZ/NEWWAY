# Руководство пользователя по results pipeline

## 1. Назначение
`results pipeline` — это единый инструмент для нормализации и агрегации результатов моделирования в проекте NEWWAY.

На текущем этапе pipeline поддерживает два источника данных:
- `van3twin_ns3`
- `simu5g`

Главная идея инструмента:
- запускать обработку через единый CLI;
- приводить результаты разных стеков к общей схеме;
- формировать выходные CSV, агрегаты, diagnostics и metadata;
- упрощать дальнейшее сравнение `VaN3Twin/ns-3` и `Simu5G`.

## 2. Точка входа
Из корня репозитория используется единая команда:

```powershell
python -m tools.results_pipeline.cli ...
```

CLI поддерживает верхний уровень справки и справку по конкретной команде.

### Верхний help
```powershell
python -m tools.results_pipeline.cli --help
```

Этот вызов показывает:
- какие команды доступны на верхнем уровне;
- общее описание инструмента.

### Help для команды build
```powershell
python -m tools.results_pipeline.cli build --help
```

Этот вызов показывает:
- обязательные и необязательные аргументы команды `build`;
- допустимые значения для `--source`;
- смысл входных параметров.

## 3. Аргументы команды build
### `--source`
Определяет, какой источник данных обрабатывается.

Поддерживаемые значения:
- `van3twin_ns3`
- `simu5g`

### `--input`
Путь ко входным данным.

Смысл зависит от `--source`:
- для `van3twin_ns3` это директория с CSV-артефактами;
- для `simu5g` это один CSV-файл после экспорта через `opp_scavetool`.

### `--output`
Директория, куда будут записаны выходные артефакты pipeline.

### `--scenario`
Имя сценария моделирования. Попадает в выходные CSV и metadata.

### `--run-id`
Необязательный идентификатор конкретного прогона.
Если параметр указан, он будет использован во всех выходных артефактах.

## 4. Использование для van3twin_ns3
Пример запуска:

```powershell
python -m tools.results_pipeline.cli build --source van3twin_ns3 --input .\tests\smoke_results_pipeline\data --output .\demo-van3twin-out --scenario v2v-cam-exchange-sionna-nrv2x --run-id demo-van3twin-001
```

### Что важно понимать
- здесь `--input` должен быть директорией;
- pipeline ищет поддерживаемые CSV по структуре заголовков;
- чужие CSV, не относящиеся к `van3twin_ns3`, должны игнорироваться.

### Какие CSV сейчас поддерживаются
#### Вариант mini phy
Ожидаются поля:
- `timestamp_ms`
- `src`
- `dst`
- `pkt_id`
- `latency_ms`
- `sinr_db`
- `rssi_dbm`
- `success`

#### Вариант mini prr
Ожидаются поля:
- `timestamp_ms`
- `src`
- `dst`
- `pkt_id`
- `prr`
- `pdr`
- `success`

#### Вариант real phy
Ожидаются поля:
- `tx_id`
- `rx_id`
- `distance`
- `rssi`
- `snr`

#### Вариант real prr
Ожидаются поля:
- `node_id`
- `prr`

## 5. Использование для simu5g
Пример запуска:

```powershell
python -m tools.results_pipeline.cli build --source simu5g --input .\tests\smoke_results_pipeline\data\simu5g_scavetool_sample.csv --output .\demo-simu5g-out --scenario minimal-simu5g --run-id demo-simu5g-001
```

### Что важно понимать
- здесь `--input` должен быть одним CSV-файлом;
- этот CSV предполагается результатом экспорта из `.sca/.vec` через `opp_scavetool`.

### Какой CSV ожидается для Simu5G
В первой версии адаптера ожидаются поля уровня:
- `run`
- `module`
- `name`
- `type`
- `value`
- `vectime`
- `vecvalue`
- `unit`
- `entity_id` (если есть)

Если CSV не соответствует этим ожиданиям, pipeline может не распознать часть данных или не сможет корректно их нормализовать.

## 6. Что создаётся на выходе
### Общие артефакты
- `normalized_events.csv`
- `normalized_metrics.csv`
- `aggregates_overall.csv`
- `diagnostics.csv`
- `run_metadata.json`
- `run_metadata.yaml`

### Дополнительно для Simu5G
- `aggregates_by_metric.csv`

## 7. Смысл выходных файлов
### `normalized_events.csv`
Базовый слой нормализованных записей.

### `normalized_metrics.csv`
Единый metric-oriented слой, к которому приводятся оба источника данных.
Именно этот файл является основной общей точкой сопоставления `van3twin_ns3` и `simu5g`.

### `aggregates_overall.csv`
Сводные агрегаты по прогону.

### `aggregates_by_metric.csv`
Для Simu5G — агрегаты отдельно по каждой метрике.

### `diagnostics.csv`
Диагностическая информация о проблемах во входных данных или замечаниях по нормализации.

### `run_metadata.json` / `run_metadata.yaml`
Контекст запуска: `run_id`, `scenario`, branch, commit, input files и время создания.

## 8. Как понять, что запуск прошёл успешно
Успешный запуск обычно выглядит так:
- команда `build` завершается без ошибки;
- выходная директория создаётся;
- в ней появляются ожидаемые CSV и metadata;
- `diagnostics.csv` пустой либо содержит только понятные замечания;
- `normalized_metrics.csv` содержит реальные строки с метриками.

## 9. Типичные ошибки пользователя
### Передан неправильный тип `--input`
- для `van3twin_ns3` ожидается директория;
- для `simu5g` ожидается файл.

### CSV не соответствует ожидаемому формату
Если структура заголовков не распознаётся, pipeline может не обработать файл или пропустить часть данных.

### Не указаны обязательные аргументы
Команда `build` требует как минимум:
- `--input`
- `--output`
- `--scenario`

### Пустой результат
Если выходная папка создана, но полезных строк нет, нужно проверить:
- формат входного CSV;
- корректность `--source`;
- содержимое `diagnostics.csv`.

## 10. Ограничения текущей версии
- прямой парсинг `.sca/.vec` без промежуточного CSV пока не поддерживается;
- Simu5G пока используется через экспортированный CSV;
- не все PHY/MAC метрики глубоко интерпретируются;
- реальное сравнение на боевом dual-run наборе ещё требует отдельной проверки.

## 12. Практический итог
На текущем этапе pipeline уже можно использовать как единый пользовательский интерфейс для двух источников данных.
Пользователь выбирает источник через `--source`, передаёт корректный `--input`, получает унифицированные выходные артефакты и может сравнивать результаты двух стеков на уровне `normalized_metrics.csv`.

## 13. Рекомендации по чистому запуску
Перед повторным запуском рекомендуется очищать старую выходную директорию или использовать новую папку для каждого прогона.

Это полезно по следующим причинам:
- не смешиваются артефакты разных запусков;
- не остаются устаревшие файлы от предыдущего источника или предыдущего сценария;
- ручная проверка и скриншоты для отчёта становятся чище и понятнее.

Примеры очистки:
```powershell
Remove-Item -Recurse -Force .\tmp-cli-van3twin -ErrorAction SilentlyContinue
Remove-Item -Recurse -Force .\tmp-cli-simu5g -ErrorAction SilentlyContinue
```

Если пользователь не хочет удалять старую папку, рекомендуется задавать новый `--output` для каждого запуска.

## 14. Дополнительные практические замечания
- команды из документации предполагают запуск из корня репозитория NEWWAY;
- перед запуском желательно активировать виртуальное окружение `.venv`;
- для `van3twin_ns3` параметр `--input` должен указывать на директорию с CSV-файлами;
- для `simu5g` параметр `--input` должен указывать на один CSV-файл после экспорта через `opp_scavetool`;
- текущий reader `van3twin_ns3` просматривает CSV только в указанной директории и не идёт рекурсивно в подпапки;
- `diagnostics.csv`, содержащий только строку заголовка, считается нормальным результатом и означает отсутствие существенных замечаний;
- `--run-id` является необязательным параметром, но для ручных проверок, скриншотов и отчёта его лучше задавать явно;
- `run_metadata.json` и `run_metadata.yaml` фиксируют branch, commit и список входных файлов, поэтому полезны для воспроизводимости;
- предупреждения Git о переводах строк `LF/CRLF` на Windows не означают логическую ошибку pipeline.
