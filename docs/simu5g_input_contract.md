# Входной контракт для Simu5G (MVP)

## Зачем нужен этот файл
Этот документ фиксирует, какие входные данные мы ожидаем от Simu5G для подключения к общему пайплайну обработки результатов.

Смысл файла:
- убрать неопределённость по входам;
- зафиксировать минимальный воспроизводимый набор артефактов;
- отделить то, что поддерживается уже сейчас, от того, что планируется позже.

## Что считается источником данных со стороны Simu5G
На стороне Simu5G исходными артефактами считаются:
- `omnetpp.ini` — конфигурация сценария;
- `*.ned` — описание структуры сети;
- `*.sca` — scalar-результаты;
- `*.vec` — vector-результаты;
- при необходимости `*.vci` — индексный файл для vector-результатов.

## Что считаем поддерживаемым входом в MVP
На текущем этапе основным и поддерживаемым входом считается не сырая пара `.sca/.vec`, а CSV-файл, полученный после экспорта результатов из OMNeT++ / Simu5G.

То есть минимальный практический путь такой:

1. Simu5G выполняет моделирование;
2. формируются файлы `.sca` и `.vec`;
3. через `opp_scavetool` результаты выгружаются в CSV;
4. именно этот CSV поступает в адаптер `results_pipeline`.

## Почему выбран именно такой путь
На текущем этапе это наиболее практичный вариант, потому что он:
- не требует сразу писать сложный низкоуровневый парсер форматов OMNeT++;
- воспроизводим;
- удобен для тестирования;
- позволяет быстро встроить Simu5G в уже существующий пайплайн.

## Минимальный обязательный набор от сценария Simu5G
Для корректной работы адаптера и для сопоставления со стеком VaN3Twin/ns-3 желательно получить следующий набор:

1. `omnetpp.ini`
2. `*.ned`
3. `*.sca`
4. `*.vec`
5. CSV-экспорт результатов после `opp_scavetool`

## Что желательно дополнительно
Помимо файлов, полезно зафиксировать:
- какие параметры сценария менялись;
- какие метрики команда считает целевыми;
- какая команда использовалась для экспорта через `opp_scavetool`;
- какие фильтры применялись при экспорте результатов.

## Предпочтительный путь экспорта
На уровне MVP мы ориентируемся на следующий процесс:

```text
Simu5G scenario
-> .sca / .vec
-> opp_scavetool export
-> CSV
-> адаптер Simu5G
-> единая схема результатов
```

## Каким должен быть экспортированный CSV
CSV должен содержать достаточно информации, чтобы можно было восстановить:
- имя метрики;
- значение метрики;
- при наличии — время;
- путь до модуля или сущности, к которой относится метрика;
- имя run или другой идентификатор прогона.

В идеале в CSV должны присутствовать поля, которые позволяют определить:
- scalar это или vector;
- к какому UE / модулю / компоненту относится запись;
- в каких единицах выражена метрика.

## Что поддерживается в первой версии адаптера
Первая версия адаптера должна уметь:
- читать экспортированный CSV;
- извлекать из него основные записи по метрикам;
- переводить их в единую схему;
- помечать источник как `simu5g`;
- передавать результат в общий downstream-пайплайн.

## Что пока не входит в MVP
На текущем этапе в MVP не входит:
- полноценный прямой парсинг `.sca/.vec` без промежуточного CSV;
- полная поддержка всех возможных типов статистик OMNeT++;
- глубокая интерпретация всех PHY/MAC метрик Simu5G;
- автоматическое восстановление всей структуры сценария только по `.sca/.vec`.

## Что нужно уточнить у команды
Чтобы сделать адаптер не только формально, но и практически полезным, нужно уточнить:
- какой CSV-формат реально получается после экспорта у Артёма;
- какие именно столбцы он получает;
- какие метрики нужно считать обязательными;
- какой минимальный сценарий Simu5G считается эталонным для этого цикла.

## Практический вывод
Для текущего цикла правильный и реалистичный путь такой:
- считать Simu5G отдельным источником данных;
- брать от него экспортированный CSV;
- нормализовать этот CSV в общую схему;
- и уже после этого делать сравнение с VaN3Twin/ns-3 на общем уровне результатов.

## Минимально ожидаемые столбцы CSV для MVP
В первой версии адаптера Simu5G ориентируется на CSV, в котором желательно присутствуют следующие поля:
- `run` или `run_id`
- `module`
- `name`
- `type`
- `value`
- `vectime`
- `vecvalue`
- `unit`
- `entity_id`

## Что обязательно для работы MVP
Минимально необходимы такие данные:
- поле с идентификатором прогона: `run` или `run_id` либо явный `--run-id` при запуске;
- путь или имя модуля: `module`;
- имя статистики: `name`;
- тип записи: `type` (`scalar` или `vector`);
- значение метрики: `value` для scalar или `vecvalue` для vector.

## Что желательно, но не строго обязательно
- `vectime` для vector-записей;
- `unit` для корректной интерпретации единиц измерения;
- `entity_id` для более удобной привязки метрик к UE/узлам;
- дополнительные признаки, по которым можно уточнить scope и смысл метрики.

## Практическая интерпретация
Если часть желательных полей отсутствует, адаптер может всё равно отработать,
но часть данных будет нормализована менее подробно или без дополнительных привязок.
