# Сравнение стеков: Simu5G и VaN3Twin/ns-3

## Зачем нужен этот файл
Этот документ фиксирует практическое сравнение двух стеков, которые рассматриваются в рамках задач CAVISE:
- `VaN3Twin / ns-3 / NEWWAY`
- `Simu5G / OMNeT++`

Смысл сравнения не в том, чтобы выбрать "лучший симулятор вообще", а в том, чтобы понять:
- какой стек уже лучше вписывается в текущий контур CAVISE;
- какой стек удобнее для воспроизводимых сетевых экспериментов;
- какой стек полезен как целевой компонент, а какой — как референсная платформа или источник отдельных решений.

## 1. Общая архитектурная позиция
### VaN3Twin/ns-3/NEWWAY
- уже встроен в текущую исследовательскую и инженерную среду;
- ближе к существующему контуру CAVISE;
- результаты уже могут появляться в CSV-артефактах;
- для него уже реализован рабочий CSV-first results pipeline.

### Simu5G/OMNeT++
- представляет собой отдельный сетевой стек;
- сценарии задаются через `NED` + `omnetpp.ini`;
- результаты формируются как `.sca/.vec`, а затем экспортируются в CSV;
- удобен как отдельный воспроизводимый сетевой стенд;
- требует дополнительного адаптера для встраивания в общий контур CAVISE.

## 2. Структура сценария
### VaN3Twin/ns-3
- сценарий ближе к уже существующей исследовательской инфраструктуре проекта;
- структура экспериментов завязана на текущий стек NEWWAY и его артефакты;
- результаты ближе к практической интеграции с транспортным контуром.

### Simu5G
- сценарий явно конфигурируется через `omnetpp.ini`;
- структура сети описывается через `NED`;
- параметры моделирования задаются довольно прозрачно;
- сценарий удобно использовать как изолированный стенд для проверки сетевых гипотез.

## 3. Управляемость параметров
### VaN3Twin/ns-3
- хорошо подходит для сценариев, уже встроенных в существующий стек;
- удобно работать в контексте текущих пайплайнов и артефактов проекта;
- параметризация зависит от структуры конкретного сценария и текущей кодовой базы.

### Simu5G
- параметры эксперимента явно задаются через `omnetpp.ini`;
- удобно варьировать количество UE, нагрузку, интервалы, часть сетевых параметров;
- хорошая воспроизводимость сетевых экспериментов при фиксированной конфигурации.

## 4. Метрики и наблюдаемость
### VaN3Twin/ns-3
- уже доступны физические и прикладные CSV-артефакты, например `phy` и `prr`;
- удобно работать с такими метриками, как `sinr_db`, `prr_value`, а также производными агрегатами;
- стек уже встроен в существующий results pipeline.

### Simu5G
- метрики доступны через `.sca/.vec` и их CSV-экспорт;
- на текущем этапе уже поддержаны:
  - `throughput_bps`
  - `delay_us`
  - `sinr_db`
  - `loss_ratio`
- для Simu5G уже реализован адаптер и отдельный pipeline, встроенный в общий CLI.

## 5. Воспроизводимость
### VaN3Twin/ns-3
- воспроизводимость опирается на текущую структуру сценариев и run-артефактов;
- metadata уже фиксируются в results pipeline.

### Simu5G
- воспроизводимость сильна на уровне конфигурации `omnetpp.ini`;
- результаты легко фиксировать как `.sca/.vec`, а затем экспортировать в CSV;
- metadata также фиксируются в нашем pipeline.

## 6. Интегрируемость в CAVISE
### VaN3Twin/ns-3
- это основной практически совместимый стек для текущей архитектуры;
- ближе к реальной интеграции с транспортным контуром CAVISE;
- уже встроен в кодовую и экспериментальную структуру проекта.

### Simu5G
- пока выступает как внешний сетевой источник данных;
- хорошо подходит как референсная платформа и как отдельный стенд;
- для прямой интеграции в CAVISE требует дополнительной прослойки;
- особенно важно учитывать ограничения относительно целевой реализации 5G NR Mode 2.

## 7. Ограничения Simu5G
На текущем этапе для Simu5G фиксируются следующие ограничения:
- пока не подтверждена полноценная поддержка целевого сценария 5G NR Mode 2 в нужном для проекта виде;
- есть риск, что Simu5G больше подходит для инфраструктурного/общего сетевого моделирования, чем для целевой sidelink-логики;
- сценарий приходится интегрировать в CAVISE не напрямую, а через адаптер данных;
- часть метрик и деталей PHY/MAC требует дополнительного подтверждения на реальных экспортированных данных.

## 8. Практический итог сравнения
На текущем этапе наиболее реалистичная картина такая:

- `VaN3Twin/ns-3` — основной практически релевантный стек для текущей линии интеграции в CAVISE;
- `Simu5G` — полезный воспроизводимый сетевой стенд, источник отдельных решений и референсная платформа для анализа метрик и параметризации;
- использовать Simu5G как полностью целевой компонент нужно только после отдельного подтверждения архитектурной пригодности для нужного варианта 5G NR V2X / Mode 2.

## 9. Что уже сделано в рамках текущего цикла
Для `VaN3Twin/ns-3` уже был реализован CSV-first results pipeline.

Для `Simu5G` в рамках текущего цикла дополнительно сделано:
- единая схема результатов;
- документ по сопоставлению метрик;
- входной контракт для Simu5G;
- адаптер чтения CSV после `opp_scavetool`;
- отдельный Simu5G pipeline;
- встройка Simu5G в общий CLI;
- тесты и ручной прогон.

## 10. Рекомендация по следующему шагу
Следующий шаг развития направления выглядит так:

1. прогнать адаптер на реальном CSV-экспорте Simu5G, полученном из рабочего сценария;
2. уточнить mapping по реальным названиям метрик;
3. провести одно практическое сравнение на реальных данных Simu5G и VaN3Twin/ns-3;
4. после этого принять решение, остаётся ли Simu5G:
   - референсной платформой,
   - источником отдельных решений,
   - или кандидатом на более глубокую интеграцию.

## Итоговый вывод
На текущем этапе `Simu5G` уже успешно встроен в общий контур обработки результатов как поддерживаемый источник данных.

Однако по архитектурному смыслу основной рабочий стек для CAVISE на данный момент по-прежнему выглядит как `VaN3Twin/ns-3`,
а `Simu5G` наиболее разумно рассматривать как воспроизводимый сетевой стенд и референсную платформу до тех пор, пока не будет отдельно подтверждена его пригодность для целевого варианта 5G NR Mode 2.
