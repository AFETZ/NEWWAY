# Сопоставление метрик: Simu5G и VaN3Twin/ns-3

## Зачем нужен этот файл
Этот документ фиксирует, какие метрики мы можем сопоставлять между двумя стеками:
- `VaN3Twin / ns-3 / NEWWAY`
- `Simu5G / OMNeT++`

Смысл документа:
- не просто перечислить метрики;
- а понять, какие из них действительно сравнимы;
- какие совпадают напрямую;
- какие можно получить только приближённо;
- и какие пока недоступны или не подтверждены.

## Общая идея
Сейчас мы сравниваем не "симуляторы целиком", а их результаты на уровне наблюдаемых сетевых метрик.
Поэтому нас интересуют такие метрики, которые:
- реально можно выгрузить из обоих стеков;
- имеют понятный физический или прикладной смысл;
- полезны для последующей интеграции в контур CAVISE.

## Базовый набор метрик для текущего цикла
На текущем этапе целесообразно считать основными такие метрики:
- `delay`
- `throughput`
- `packet_loss` / `reliability`
- `sinr`

Именно они дают наиболее устойчивую и понятную основу для сравнения двух стеков.

## Таблица сопоставления
| Общая метрика | VaN3Twin/ns-3 | Simu5G | Статус сопоставления | Комментарий |
|---|---|---|---|---|
| `sinr_db` | `phy_with_sionna_nrv2x.csv: snr` | ожидается как PHY-статистика / scalar или vector export | прямое или почти прямое | одна из самых полезных физических метрик |
| `prr_value` | `prr_with_sionna_nrv2x.csv: prr` | может отсутствовать в явном виде | частичное | в Simu5G, возможно, придётся выводить через packet loss / reception statistics |
| `pdr_value` | пока не всегда есть в явном виде | может отсутствовать в явном виде | слабое | не стоит делать ключевой метрикой первого этапа |
| `delay_us` | может выводиться из логов или derived-слоя | обычно ожидается как delay / packet delay statistic | хорошее | одна из главных прикладных метрик |
| `throughput_bps` | возможен как derived throughput | обычно ожидается как throughput statistic | хорошее | одна из самых удобных и сравнимых метрик |
| `loss_ratio` | можно выводить из reception/delivery данных | может быть выражен через packet loss / dropped packets | хорошее или среднее | полезна как общая метрика надёжности |
| `bler` | не всегда доступен в текущем CSV-first слое | может быть связан с PHY-уровнем, но надо подтверждать export | неопределённое | полезно, но не обязательно для MVP |
| `rssi_dbm` | есть в `phy_with_sionna_nrv2x.csv` | не гарантировано как основная экспортируемая метрика | среднее | полезно, но менее универсально для сравнения, чем SINR |
| `distance_m` | есть в `phy_with_sionna_nrv2x.csv` | обычно не является сетевой метрикой сама по себе | косвенное | полезна как поясняющий фактор, а не как итоговая KPI |

## Практический вывод по метрикам
Для первого рабочего этапа сравнения стеков имеет смысл опираться в первую очередь на:

1. `sinr_db`
2. `delay_us`
3. `throughput_bps`
4. `loss_ratio` или близкую метрику надёжности

Эти метрики одновременно:
- достаточно информативны;
- понятны для команды;
- подходят для дальнейшей интеграции в общий аналитический пайплайн.

## Что считается прямым совпадением
Прямым совпадением считаем ситуацию, когда:
- в обоих стеках есть метрика с сопоставимым смыслом;
- она может быть приведена к одной единице измерения;
- и её можно без сильной дополнительной интерпретации положить в общий формат.

Примеры:
- `sinr_db`
- `delay_us`
- `throughput_bps`

## Что считается частичным совпадением
Частичным совпадением считаем ситуацию, когда:
- метрика в одном стеке есть напрямую;
- а в другом должна быть получена через близкую статистику или производную оценку.

Пример:
- `prr_value` для ns-3 может быть доступен сразу,
- а в Simu5G его, возможно, придётся выводить через статистику успешного/неуспешного приёма или packet loss.

## Что пока не стоит делать основой сравнения
На первом этапе не стоит делать центральными такие метрики:
- `pdr_value`, если она не подтверждена в обоих стеках;
- `bler`, если не подтверждён стабильный экспорт;
- узкоспециальные PHY/MAC показатели, которые трудно одинаково интерпретировать.

## Что нужно уточнить у команды
Для окончательной версии таблицы нужно получить:
- реальные экспортированные CSV из Simu5G;
- список названий метрик после `opp_scavetool`;
- подтверждение, какие метрики команда считает обязательными для сравнения;
- понимание, какой сценарий Simu5G будет считаться минимально воспроизводимым эталоном.

## Итог
На текущем этапе можно уверенно закладывать основу сравнения по следующим направлениям:
- физическое качество связи (`sinr_db`),
- прикладная задержка (`delay_us`),
- пропускная способность (`throughput_bps`),
- надёжность передачи (`loss_ratio` / `prr_value` в приближённом общем смысле).

Именно этот набор выглядит наиболее устойчивым и пригодным для первого слоя унификации между `VaN3Twin/ns-3` и `Simu5G`.
