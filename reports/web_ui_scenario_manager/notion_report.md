# Отчет по Web UI для запуска сценариев

## 1. Что это за результат

В рамках цикла был подготовлен отдельный инструментальный слой проекта:
локальный Web UI для запуска сценариев, просмотра результатов и перехода от
настройки эксперимента к его артефактам без ручного перебора shell-команд.

Это не замена самим сценариям и не отдельная научная модель. Это интерфейсный
контур, который делает уже существующие сценарии более доступными для:

- демонстрации;
- повторного запуска;
- первичной аналитики;
- передачи работы другому человеку без необходимости сразу читать внутреннюю
  структуру репозитория.

## 2. Зачем понадобился Web UI

По мере роста числа сценариев стало видно, что у проекта есть типичная
исследовательская проблема: runnable-слой существует, но пользоваться им
неудобно без знания внутренних команд, переменных окружения и структуры output.

На практике это приводит к трем барьерам:

1. новый человек не знает, какой сценарий запускать и чем они отличаются;
2. даже после запуска не всегда понятно, где искать результат и как быстро
   открыть meaningful summary;
3. для показа руководителю или коллеге неудобно каждый раз объяснять workflow
   через терминал.

Именно эту проблему и решает Web UI.

## 3. Что именно реализовано

### 3.1. Единая точка входа

Интерфейс поднимается как локальное Streamlit-приложение и открывает единый
контур работы:

- выбор сценария;
- чтение его описания;
- настройка параметров;
- запуск;
- просмотр summary;
- просмотр графиков;
- просмотр прошлых запусков.

### 3.2. Реестр сценариев

В UI заведены пять сценариев:

| Сценарий | Назначение |
|---|---|
| `burst_vs_random_loss` | сравнение пакетных и случайных потерь |
| `density_scaling` | влияние плотности трафика на безопасность и связь |
| `latency_vs_loss_tradeoff` | компромисс между loss и delay |
| `truck_lane_change` | фиксированный lane-change кейс для демонстрации и дипломных артефактов |
| `intersection_crash` | фиксированный junction crash кейс для демонстрации и дипломных сводок |

Ключевой смысл в том, что UI работает не как набор кнопок без контекста. Для
каждого сценария в реестре есть:

- название;
- описание;
- научная цель;
- гипотеза;
- настраиваемые параметры;
- ожидаемые типы артефактов.

То есть интерфейс помогает не только запустить сценарий, но и понять, зачем он
вообще существует.

### 3.3. Параметризация запуска

В интерфейсе реализована форма настройки параметров. Она позволяет без ручного
редактирования shell-команды изменять:

- длительность симуляции;
- использование GUI;
- включение или отключение Sionna;
- sweep-параметры для исследовательских серий;
- выходную директорию через `OUT_BASE` или `OUT_DIR` в зависимости от типа
  сценария.

Таким образом UI не скрывает исследовательскую логику, а делает ее более
управляемой и менее хрупкой.

### 3.4. Запуск и потоковый лог

После нажатия на запуск интерфейс:

- вызывает сценарный `run.sh`;
- передает параметры через переменные окружения;
- создает output-директорию;
- показывает потоковый лог выполнения;
- сохраняет контекст последнего запуска для дальнейшего просмотра.

Это важный практический момент: UI здесь не декоративный. Он действительно
управляет запуском сценария и возвращает пользователя к результатам.

### 3.5. Просмотр результатов

После завершения прогона интерфейс умеет:

- находить summary CSV;
- показывать их в табличном виде;
- подсвечивать ключевые численные метрики;
- отображать статические графики;
- строить интерактивные графики там, где это возможно;
- подгружать прошлые прогоны из каталога результатов.

В результате возникает единый цикл:

`описание сценария -> запуск -> summary -> графики -> сравнение прошлых прогонов`

## 4. Как устроен UI внутри

Архитектурно результат разбит на четыре понятных модуля:

| Модуль | Роль |
|---|---|
| `app.py` | сам Streamlit-интерфейс, навигация и страницы |
| `scenarios.py` | реестр сценариев, их метаданных и параметров |
| `runner.py` | запуск сценариев и передача логов в интерфейс |
| `visualizer.py` | построение графиков и dashboards по артефактам |

Это хорошее разделение ответственности:

- UI-логика не смешана со списком сценариев;
- запуск сценариев не смешан с визуализацией;
- список сценариев можно расширять без переписывания всего интерфейса.

## 5. Что подтверждает, что это не макет, а рабочий инструмент

### 5.1. Подтвержденный локальный запуск

Для UI подтвержден реальный локальный запуск Streamlit. Отдельным probe
зафиксировано:

- приложение поднимается локально;
- отвечает по HTTP;
- отдает страницу с кодом `200 OK`.

### 5.2. Контрактные тесты

Подтвержден успешный прогон unit-тестов:

- проверяется состав реестра сценариев;
- проверяется существование всех зарегистрированных `run.sh`;
- проверяется корректное использование `OUT_BASE` и `OUT_DIR`;
- проверяется, что callback вызывается в том же потоке, что и UI.

Иными словами, у результата есть не только код, но и минимальный проверочный
контур.

### 5.3. Интеграция с реальными сценариями

Особенно важно, что два thesis-grade сценария — `truck_lane_change` и
`intersection_crash` — уже подключены в UI как реальные сценарии, а не как
заглушки.

Это значит, что интерфейс опирается на живые, уже доказательные кейсы проекта.

## 6. Почему этот результат важен

Web UI важен не потому, что “у проекта появился интерфейс”. Его ценность более
прикладная:

1. он снижает порог входа в проект;
2. он облегчает демонстрацию сценариев руководителю и коллегам;
3. он делает воспроизводимость сценариев лучше;
4. он собирает в одной точке сценарий, параметры и результаты;
5. он снижает зависимость от того, кто именно из команды помнит нужные команды.

Для исследовательского проекта это отдельная полезная работа, потому что она
повышает управляемость всего экспериментального контура.

## 7. Ограничения и честные оговорки

Важно честно зафиксировать, что это именно локальный research-интерфейс, а не
production web-platform.

Текущие ограничения такие:

- интерфейс рассчитан на локальный запуск;
- он не заменяет quality control самих сценариев: если сценарий дал слабые
  артефакты, UI это только покажет, но не исправит;
- browser-automation и автоматическое снятие скриншотов зависят от наличия
  системных браузерных зависимостей в окружении;
- интерфейс уже полезен для запуска и просмотра результатов, но может быть
  дальше усилен отдельной страницей сравнения запусков и более богатой
  фильтрацией артефактов.

## 8. Формулировка задачи на цикл

**Физулин А.В.**

**Зона ответственности:** Web UI для запуска сценариев, просмотра результатов и
снижения порога входа в экспериментальный контур проекта.

**Содержательно задача состояла в том, чтобы:**

1. собрать единый интерфейс для запуска сценариев;
2. оформить реестр сценариев с понятными описаниями и параметрами;
3. связать UI с реальными launcher-скриптами;
4. добавить просмотр summary, графиков и прошлых запусков;
5. зафиксировать базовые тесты и документацию.

**Результат на выходе:**

- работающий локальный Streamlit UI;
- единый реестр из 5 сценариев;
- запуск сценариев из интерфейса;
- просмотр summary CSV и графиков;
- базовый тестовый контур;
- документация по использованию UI.

## 10. Что логично делать дальше

Следующий естественный шаг по этому направлению:

1. добавить отдельный слой сравнения нескольких запусков;
2. усилить фильтрацию артефактов и summary в интерфейсе;
3. добавить более явное разделение между доказательными кейсами и sweep-режимами;
4. при необходимости подготовить boss-facing версию UI с более полированной
   визуальной подачей.
